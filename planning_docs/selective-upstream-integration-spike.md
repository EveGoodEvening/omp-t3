## Atomic Stop facts and constraints

- `src/modes/rpc/rpc-mode.ts:541-555,2088-2104`: when accepted, atomic abort invalidates earlier accepted user input via the input gate. The handler synchronously calls `session.clearQueue({forInterrupt:true})`, then stops the goal and builtin commands, awaits `session.abort`, and returns `abort_and_restore_queue`. `src/session/agent-session.ts:11160-11220` includes user-authored messages already dequeued but not recorded and clears user queues; non-user visible queued messages have separate interrupt preservation. This is materially safer than `get_state` + per-message removal.
- `rpc-mode.ts:737-778`: response fitting may mark `imagesDropped` and `truncated`, with only an oldest-first prefix returned after withdrawal. The Pi clear interface represented by upstream accepts text arrays; images cannot be represented. **Do not claim every withdrawn text can always be returned:** truncation has already discarded omitted values. Preserve/report truncation and image loss explicitly, e.g. an observable notice, rather than silent success. A stricter all-text acceptance criterion is impossible against this OMP response limit without upstream API changes.
- Failure is not proof of no withdrawal: `clearQueue` occurs before the awaited abort, and dispatcher catches handler errors (`rpc-mode.ts:496-499,640-643`). Only a positively identified unsupported-command response proves this handler did not run; other failures, EOF, and timeout are indeterminate. Never automatically repeat atomic or plain abort on indeterminate failure. Unsupported plain-abort fallback can execute stranded queued input; explicitly signal non-atomic degradation and never claim restored texts. Whether fallback versus stop/terminate should be the product policy needs a deliberate decision; safest is fail closed, report unsupported, and do not issue plain abort automatically.
- Existing `SettlementTracker.handleUpstreamFrame` abort invokes `onAbort` synchronously; proxy `onAbort` emits interrupted cards and sends hard `cancel_subagent` before settlement. Idle abort returns `agent_settled` immediately; active abort marks `sawAbort` and emits `agent_end` plus `agent_settled` on the eventual cycle end. These paths must execute **once per actual atomic Stop**, not only on receipt of a following abort. Keep cancellation before atomic child write and keep late-child cancellation window semantics. Repeated stops require deduplication of already-terminal subagent cards, but must not suppress cancellation of newly observed children.
- Upstream adapter starts the atomic Stop on clear and buffers all downlink until the follow-up abort. `flushAll()` only flushes buffers, not `operations`/`awaitingAbort`: prompt then later abort can attach to a stale clear. Repeated clear similarly flushes but leaves the earlier waiter. A lack of next abort holds unrelated RPC frames without limit. Matching only an internal ID without validating response `command` also risks consuming a conflicting frame; reserve unique namespace and require both ID and command, with collision handling for client IDs.

## One concrete alternative: response-scoped terminal barrier

[INFERENCE/design, not implemented] Treat each clear as a complete Stop, not as a half-operation dependent on a second request. Hold only the terminalization needed to keep T3's active turn until the clear response; do not hold the full downstream stream. In particular:

1. On `clear_queue`, create one generation-scoped operation with a unique opaque internal ID, retain the original ID with its JSON type, arm the settlement output barrier, invoke the existing abort transition/sweep, and write exactly one atomic request. Output subagent terminal cards immediately before a possible settle. If idle, retain the one synthesized terminal. If active, feed all OMP frames through the existing tracker in order; forward ordinary output including `agent_end`, but intercept the resulting `agent_settled` until clear is answered. Never hold arbitrary frames or unrelated response IDs. Apply the same barrier to *all* paths that can finalize T3, including translated `session_settled` and command-only/fallback settles, and deduplicate terminals by turn generation. During a pending barrier, translate normal `get_state` immediately but include the shim's own outstanding finalization in `pendingMessageCount`; otherwise T3's idle probe can settle before clear. This represents actual proxy-side pending work, not OMP queue size; avoid modifying unrelated fields.
2. If an `abort` arrives **while this clear's atomic response is still pending and without an intervening mutating input**, record its original ID as a correlated follower. Do not send another abort or invoke the sweep twice. Repeated clear requests and other mutating input must be serialized in a bounded queue (or explicitly rejected while busy); never silently drop or hold indefinitely. Unrelated read-only RPCs, including `get_state`, pass immediately. On matching success, send clear response first, then release the held terminal, then answer an already-arrived follower abort; retire all association state immediately. Missing follower never prevents response or terminal delivery. An abort arriving after retirement is a fresh atomic Stop. A lone abort also starts a fresh atomic Stop, gets an `abort` response with its original ID after the atomic result, and uses the same settlement lifecycle.
3. No bounded algorithm can perfectly identify a late follower versus an independent later abort: the protocol contains no common Stop ID. A follower after retirement causes a second atomic abort, rather than consuming a stale token; if a new prompt intervened it can cancel that prompt. This unavoidable ambiguity is a real contract limitation, not solved by timers. Strict once-per-gesture semantics across arbitrary delay require a T3 protocol correlation ID or ordering guarantee. The design chooses safe fresh-stop semantics over stale association. Do not advertise exactly one atomic request per T3 gesture unless the client supplies that guarantee.
4. Set a finite response deadline and cap terminal/mutation storage. If atomic reply never arrives or is ambiguous, report error and release pending client requests/terminal in a defined order, invalidate operation, and fail closed against further mutating input or terminate the broken provider connection; do not retry an operation that may already have withdrawn data. Child exit/stream errors must also resolve all pending requests and release storage. A fixed cap must fail explicitly, not silently lose a terminal. Late internal responses from retired generations must be consumed without contaminating new generations. This timeout implies a missing clear response cannot be faithfully delivered; explicit transport failure is preferable to indefinite hang.
5. On clearly unsupported atomic command, return failed clear (or failed lone abort), retire the association, surface the lack of atomic Stop, and avoid claiming queue removal. Existing process/session may remain busy: explain this limitation; policy may require terminating it if Stop must be guaranteed. For other failure return an indeterminate failure because withdrawal may already have happened. Do not assume any failure means no abort. Preserve `imagesDropped`/`truncated` diagnostics.

This is a proposal, not proof of complete implementation. Critical integration caveats: `session_settled` and `agent_end` can arrive before or after atomic response, and the terminal gate must never emit duplicate or stale terminal events into a later prompt. Serializing prompt/session changes until the operation reaches a terminal state avoids cross-generation tracker corruption; do not queue arbitrary unbounded input. The helper cannot just split arbitrary serialized strings without preserving multiline output order; adapt the tracker to expose terminal frames explicitly. Confirm T3's handling of failed clear and shim notices with a synthetic adapter integration test before adoption.

### Required behavioral acceptance scenarios

- Active and idle Stop; clear response precedes *every* settle route, interrupted cards precede settle, cancellation writes precede atomic request, no duplicate terminal. Background-wake and late child events retain current cancellation semantics.
- Paired abort before atomic response, paired abort after response, lone abort, repeated clear/abort, clear with no abort then fresh prompt and later Stop; IDs include numbers, strings, missing/null as supported by the actual client/OMP contract. Late atomic response cannot complete a new generation.
- Unrelated `get_state` and other response IDs pass promptly while a Stop awaits OMP; a pending probe cannot cause early client finalization. Test terminal-before-response, response-before-terminal, source `agent_end` ordering, and a sustained stream proving memory remains bounded.
- `truncated`, `imagesDropped`, empty texts, duplicate texts and both queue orders; distinguish omitted data from empty queue. Unknown command, post-withdraw thrown error, timeout, EOF, and input-cap exhaustion are observable and cannot report atomic success or blindly replay the abort.
- Explicitly verify client assumptions: whether abort is emitted only after awaiting clear, how timeout/error is consumed, whether synthetic error notices are visible, and what T3 does to frames after `agent_settled`. The patch's claims are not independent runtime evidence.

## Enabled-tool lifecycle fit

- `extensibility/extensions/types.ts:2167-2174` declares `getActiveTools(): string[]` and async `setActiveTools(names)`; `runtime-init.ts:127-130,213-214` binds them before awaited `session_start`. In 18.20.0 `getActiveTools` actually calls `getEnabledToolNames`, including `xd://` mounted names (`session/session-tools.ts:865-876`), not merely top-level model tools. `setActiveToolsByName` ignores unknown registry names, serializes mutation and applies the supplied complete selection (`session-tools.ts:2336-2347`). It is not a simple set difference mutation.
- A routing-only extension, installed **only** when `OMPT3_DELEGATE_TASKS !== '0'` and no explicit `--tools` in either CLI form, can await `setActiveTools(getActiveTools().filter(n => n !== 'task'))` only when task exists. Hook `session_start`, `session_tree`, and `before_agent_start` to cover initialization, tree restoration, and per-user-turn rebuilds. `before_agent_start` runs in extension registration order and handlers are awaited (`runner.ts:2645-2675`); a later extension may re-enable task after this hook. Hook errors/timeouts or later plugin mutations can also defeat filtering. These hooks are not a security boundary. Consider a routing-only `tool_call` guard if the contract requires enforcement even after later re-enablement, but it must be disabled on explicit tools/opt-out and distinct from model-policy blocking.
- [INFERENCE] Filtering the *current enabled names* avoids the fixed-list probe's systematic loss of configured/plugin/MCP names, but exact preservation is **not proven**: `setActiveToolsByName` may recalculate xdev presentation, pinned runtime selections and current mounts (`session-tools.ts:2350-2361,2410-2440`). A later registration or concurrent mutation can change the set between get and set; extension order and MCP reload matter. This API cannot atomically remove one name. Test mounted/unmounted MCP, late plugin registration and restoration, and compare name sets and top-level vs mounted presentation. If exact preservation cannot be verified, don't claim it or silently replace the current approach.
- Preserve explicit `--tools` unchanged including invalid names and `task`; don't append routing instruction or inject routing hook. `OMPT3_DELEGATE_TASKS=0` likewise restores OMP's native resolution and no routing appendix. `src/cli.js:143-165` already makes model-policy arguments independently and retains the native concurrency cap on both paths. `src/subagent_policy.js:38-54,77-93` separately blocks native task when opt-in model policy is active, even with explicit tools or opt-out, and checks T3 delegation after role-based model fill. Do not remove, default-enable, or conflate this guard with routing. `src/extension_compat.js` has separate adapted-bridge enforcement and model inheritance; retain it.
- [INFERENCE] `session_tree` is emitted on tree navigation (`agent-session.ts:15088-15093`); it is not demonstrated here as a universal session switch or extension reload event. Session-start replay for extensions loaded later exists (`runner.ts` comments around 1223). Lifecycle and registration ordering should be validated under a hermetic mocked extension harness and, if safe isolation can be established, a separately gated OMP runtime test. No such runtime test was performed here.
