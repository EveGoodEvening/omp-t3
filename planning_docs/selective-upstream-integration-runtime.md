## Actual T3 Stop flow (release source)

- `adapter.ts:2999-3043`: `interruptTurn` first finds and validates the active turn and sets `turn.interrupted = true`. Ordinary Stop **awaits** `clearNativeQueue(turn)` and only then issues and awaits `request({type:"abort"})`. Thus the usual abort arrives after clear has answered, not while clear is pending. Abort failure resets `interrupted` to false and propagates an adapter interrupt error. `requestRuntimeRestart`, `settleWhenIdle`, and compaction select termination paths; when restart is explicitly requested and not already settling, T3 awaits clear and a two-second abort (failure ignored), captures tree refs, and terminates. Other termination-path conditions can terminate without this clear/abort pair. These are not all equivalent to a lone abort.
- `adapter.ts:1449-1482`: clear has a **2,000 ms** timeout; errors including unknown command, timeout, and transport errors are converted to an empty list, after which abort is still sent. Successful `steering` and `followUp` arrays are concatenated, only string elements retained. If nonempty, the notice is emitted only while the *same* `activeTurn` still exists, under `sessionEventPermit`; the count includes empty image-only text, empty strings are omitted from the displayed body, and the complete notice is truncated to 2,000 characters. This is a completed `system_notice` turn item, not restoration into the composer. If clear fails, T3 silently treats it as empty. The T3 test at `adapter.test.ts:4690-4740` covers an unknown clear command followed by abort and checks the order and notice, but does not prove OMP atomic semantics.
- `adapter.ts:1718-1724`: `finalizeTurn` immediately sets `state.activeTurn = null` before finishing output items, capturing tree refs, reading usage, and emitting final turn status. At `2179-2199`, an `agent_settled` for an interrupted turn directly finalizes it. Therefore any terminal emitted before the clear response can prevent the clear notice. `extension_ui_request` method `notify` creates a system notice only if an active turn exists and the message is nonempty (`1485-1497`); stderr is logged only as length (`rpc.ts:398-409`), not a user-facing notice. A diagnostic must arrive in time and in a T3-recognized form; a failed clear alone is not a reliable user-facing warning.
- `adapter.ts:1835-1865,2333-2371`: asynchronous `get_state` settle probes carry a turn ID and generation. For a matching, non-compacting turn, an idle result (`isStreaming` and `isCompacting` not true; pending count zero or missing) finalizes independently of `agent_settled`. A failed pre-activity probe finalizes immediately; a failed post-activity probe retries up to three times then terminates the connection. Already-issued probe replies can therefore finalize during clear even if the shim holds every terminal event. `get_state` response frames go to the RPC request waiter, not the normal event stream (`rpc.ts:299-318`). A terminal-only output barrier by itself is **not proven sufficient** to preserve the notice. Passing unrelated RPC responses promptly and simultaneously preventing an already-pending idle probe from finalizing requires further integration design; do not claim both properties merely from delaying `agent_settled`.
- `rpc.ts:299-318` resolves string-ID success responses with `data`; failures become `PiRpcError` with error detail truncated to 200 characters. T3's normal clear handler swallows this failure, whereas its abort handler propagates errors. Late or unmatched replies are routed as events. These observations are source-derived, not a live T3 test.

## Bounded Stop recommendation

Use an atomic `abort_and_restore_queue` for a clear gesture or lone abort; preserve the existing child-cancellation/sweep-before-atomic-write invariant and process each actual operation once. A finite atomic deadline must be **shorter than T3's 2-second clear timeout**, with margin for transport and notice scheduling; after timeout or ambiguous generic failure, assume withdrawal may already have occurred, report indeterminate outcome, and terminate/fail the provider transport rather than retry either atomic or plain abort. Explicit unsupported-command failure likewise must not silently fall back to plain abort: the latter may execute stranded queued input. Failing the clear alone is insufficient because this T3 client deliberately proceeds to abort even on clear failure; prevent that unsafe second operation and make failure visible, preferably by terminating the broken session with a user-visible provider error. Termination does not guarantee recovery of withdrawn data.

On a successful clear, retain at most **one** completed-clear follower token tied to the unchanged input generation. A following abort consumes it and receives an acknowledgement without a second atomic abort; invalidate it on every new mutating input, failure, timeout, or transport closure. Also associate an abort that arrives while the atomic response is pending. This matches the actual awaited-clear T3 path; W03's immediate retirement and treatment of every post-completion abort as a fresh Stop would normally abort twice for this client. The token is necessarily ambiguous: a genuine independent abort with no intervening mutation can be consumed. Without a shared gesture ID, no time/generation heuristic distinguishes the cases. Do not advertise exact attribution. No old operation or token may survive new mutation.

Retain only bounded terminalization, not all frames; unrelated RPCs should pass. Keep clear response before any held terminal and deliver a correlated abort response in a defined order. However, the independent already-in-flight settle-probe race above remains an open correctness issue: a terminal barrier cannot delay T3's internal probe. Resolve and test that race against a realistic T3 client before calling the design firm; merely buffering all `get_state` responses violates liveness, and fabricating streaming state changes semantics. Cap in-flight mutations or reject them explicitly and terminate on indeterminate operation; consume late internal responses without matching future generations. Source and W03 establish OMP response fitting may truncate withdrawn text or drop images after withdrawal. Surface `truncated`/`imagesDropped` while T3 can still display a notice; neither the shim nor T3 can reconstruct omitted content. T3 itself further limits displayed text to 2,000 characters and does not restore it to the composer.

## Active-tool evidence and hermetic model

In OMP 18.20.0, `src/modes/runtime-init.ts:127-130,213-214` binds `getActiveTools` to `session.getEnabledToolNames`, `setActiveTools` to `setActiveToolsByName` (possibly through `filterActiveTools`), then awaits `session_start`. `src/session/session-tools.ts:865-876` unions enabled names with live `xd://` mounts. `2336-2347,2415-2440` normalizes the complete replacement selection, classifies mounts using the *current* mount set, pins non-mounted runtime selections and applies them; `2350-2362` explicitly says exact snapshot restoration needs a separate mounted subset. Unknown registry names are ignored. `src/extensibility/extensions/runner.ts:2657-2675` runs `before_agent_start` handlers in extension registration order; a later handler can re-enable task. `runner.ts:1222-1224` also documents replay of session_start for extensions added later.

A no-file, no-OMP Node harness was run with `node <<'NODE'` in the shell. It modeled a registry, complete-set replacement, current mount partition, three sequential lifecycle hooks, and later re-enablement. Starting with `task`, configured `read`, `plugin_probe`, `mcp__fixture__query`, and mounted `mounted_probe`, each `get().filter(n => n !== 'task')` followed by modeled `set` asserted the same other names and mounted partition for `session_start`, `session_tree`, and `before_agent_start`. Output was:

```text
session_start {"top":["read","plugin_probe","mcp__fixture__query"],"mounted":["mounted_probe"]}
session_tree {"top":["read","plugin_probe","mcp__fixture__query"],"mounted":["mounted_probe"]}
before_agent_start {"top":["read","plugin_probe","mcp__fixture__query"],"mounted":["mounted_probe"]}
later extension can re-enable task
```

This is a deliberately simplified behavioral model, **not** the actual OMP API, hook dispatch, registry, MCP implementation, or xdev presentation. It demonstrates the candidate invariant only under its assumptions, not runtime preservation. In particular it does not cover asynchronous registry/mount changes between read and write, names absent from registry, transport-only write, presentation recalculation, late plugin/MCP activation or restoration. The source shows the read and mutation are separate; it does not prove a stable snapshot. Recommend keeping P4 gated until an isolated no-model OMP RPC fixture or an actual installed-class harness proves the relevant presentation and lifecycle cases. Do not replace fixed probing with an unconditional preservation claim on this evidence.

## Remaining external/proof blockers

1. A safe live OMP fixture needs a verified filesystem namespace exposing only the runtime dependencies and scratch HOME/XDG/agent directory/cwd, cleared environment, no discovered extensions, explicit trusted fixture, no MCP/auth/config, and network denial; all OMP launches must be heavy-gated. User namespaces alone did not prove those conditions. No real session was attempted.
2. Real installed T3 bundle-to-release equivalence is only partially corroborated by the distinctive embedded notice literal. A controlled actual-client integration test is needed for output/notice/probe ordering, timeout, transport termination, and UI presentation. No T3 server was restarted.
3. A protocol-level Stop correlation ID and a lossless atomic withdrawal response would require upstream changes; neither can be supplied by this shim. The generation-token ambiguity and already-lost text/images remain explicit limitations.
